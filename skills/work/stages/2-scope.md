# 2. scope — 구현 범위 확정

## 입력

- `이슈 요약` (1-intake 출력)

## 절차

1. 영향 범위를 탐색한다. 이슈가 가리키는 기능의 진입점(컨트롤러·핸들러·커맨드), 핵심 로직, 테스트 위치, 설정을 찾는다. 코드베이스가 크면 Agent 도구(`subagent_type: Explore`)에 맡기고, 작으면 Grep·Glob으로 직접 본다. 결론(파일 목록과 이유)만 가져온다.

2. 범위 문서를 만든다.
   ```
   목표       한 문장. 이슈가 닫히려면 무엇이 참이어야 하는가
   포함       이번에 하는 것. 항목마다 근거
   제외       이슈에서 파생되지만 이번에 안 하는 것. 왜 빼는지 (별도 이슈 제안 포함)
   영향 범위  파일·모듈 목록. 새로 만드는 것 / 고치는 것 구분
   리스크     동시성·마이그레이션·외부 연동처럼 조심할 지점, 아직 확실하지 않은 것
   ```
   "포함"이 5개를 넘으면 이슈가 너무 크다는 신호다. 분할을 제안한다.

3. 이슈 코멘트 draft를 만든다. 첫 줄에 마커를 둔다. 재개 시 이 마커로 찾는다. 이전 `scope` 코멘트를 갱신하는 것이면 둘째 줄에 "(이전 범위 대체)"를 적는다.
   ```
   <!-- agentic-devflow:scope -->
   ## 구현 범위
   (위 형식 그대로)
   ```

## 게이트

1. **범위 확정** — 범위 문서를 보여주고 묻는다: "이 범위로 진행할까요?" 이견이 있으면 고쳐서 다시 확인한다. 확정 전에는 코드를 고치지 않는다.
2. **코멘트 게시** — draft를 보여주고 승인받은 뒤 게시한다.
   ```bash
   gh issue comment <n> --body-file <임시파일>
   ```
   - 게시가 실패하면 **중단**한다. 이 코멘트는 재개의 정본이므로 게시되지 않은 채 다음 단계로 가면 다음 세션이 범위를 잃는다. 원인(권한·네트워크·본문 크기)을 보고하고 재시도 여부를 묻는다.
   - 이미 같은 마커의 코멘트가 있으면(재개) 새 코멘트로 갱신 이력을 남긴다. 기존 코멘트를 조용히 덮어쓰지 않는다.

## 출력

- `확정된 범위` (위 형식)
- 범위 코멘트 URL
