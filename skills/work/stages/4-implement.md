# 4. implement — 구현

## 입력

- `계획` (3-plan 출력, 또는 재개 시 이슈의 `plan` 코멘트)
- 작업 브랜치에 체크아웃된 상태

## 절차

계획의 단계를 순서대로 수행한다. 단계마다:

1. **구현** — 그 단계의 파일만 건드린다. 계획에 없는 파일을 고치게 되면 이유를 기록한다 (아래 "계획 이탈").
2. **검증** — 계획에 적은 명령을 실행한다. 실패하면 고친다. 실패한 채로 다음 단계나 커밋으로 가지 않는다.
3. **커밋** — 검증 통과 후 그 단계의 변경만 커밋한다.
   - 메시지는 프로젝트 커밋 컨벤션(CLAUDE.md)을 따른다. 없으면 Conventional Commits, 한글 제목 50자 이내.
   - `git add -A`로 무관한 파일을 쓸어 담지 않는다. 대상 파일을 지정한다.

부수 규칙:

- **계획 이탈** — 계획과 다르게 가야 하거나(설계 변경, 단계 추가·삭제) 막혔던 문제를 풀었으면 이슈 코멘트로 남긴다. 나중에 "왜 이렇게 됐지"의 근거가 된다.
  ```
  <!-- agentic-devflow:note -->
  ## 진행 메모
  - 3단계에서 StockRestorer를 별도 클래스로 뽑음. CancelService가 이미 400줄이라.
  - 트러블슈팅: H2에서 낙관적 락 테스트가 통과하지 않아 Testcontainers MySQL로 전환.
  ```
- **push 안 함** — 7-ship에서 한다. 사용자가 중간 push를 요청하면 `git push -u origin <branch>`.
- **도메인 지식** — 프로젝트에 맞는 스킬(예: Spring 설계·테스트 규칙)은 description으로 자동 발화한다. 이 단계가 이름을 불러 호출하지 않는다.
- **범위 밖 발견** — 작업 중 다른 버그·개선점을 보면 고치지 말고 메모해 두었다가 7-ship에서 별도 이슈 등록을 제안한다.

## 게이트

- 계획 이탈 코멘트: draft를 보여주고 승인 후 게시.
- 같은 단계의 검증이 **3회** 연속 실패하면 멈추고 보고한다. 무엇을 시도했고 무엇이 남았는지 함께.

## 출력

- 커밋 목록: `git log origin/<base>..HEAD --oneline`
- 마지막 검증 결과 (명령과 요약)
- 범위 밖 발견 메모 (있으면)
