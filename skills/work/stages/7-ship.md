# 7. ship — PR

## 입력

- `base`, 현재 브랜치, 이슈 번호 `n`, `이슈 요약`
- 전체 검증 명령 (계획에서. 없으면 사전 확인 5항의 방법으로 확정하거나 묻는다)
- 6-apply 출력 (리뷰를 거쳤으면). 리뷰 없이 왔으면 "리뷰 정보 없음"
- 설정 `merge`, `merge_method`
- 범위 밖 발견 메모 (4-implement)

## 절차

순서를 지킨다. 히스토리가 PR보다 먼저다.

1. **잔여 리뷰 확인** — 이슈에 `<!-- agentic-devflow:review -->` 코멘트(치명·중요 잔여)가 있으면 목록을 보여주고 **그대로 PR을 낼지 명시적으로 확인받는다.** 확인 없이 진행하지 않는다.

2. **전체 검증** — 전체 검증 명령을 실행한다 (단계별 검증과 별개). 실패하면 PR을 만들지 않는다. 리뷰를 거쳤으면 6-apply로, 아니면 4-implement로 돌아가 고친다. 검증 명령이 "자동 검증 수단 없음"이면 실행 없이 다음으로 가되 PR 본문에 그 사실을 적는다.

3. **히스토리 문서** — 다음 중 하나면 히스토리를 남긴다: 레포에 `docs/history/`가 있음, **또는** CLAUDE.md(및 `@import`된 컨벤션 문서)가 히스토리 기록 규칙을 선언함(저장소 디렉토리든 외부 도구든). 규칙이 정한 형식·위치대로 작성하고, 레포 안 파일이면 커밋한다. 규칙을 찾지 못하면 **건너뛰되 "히스토리 규칙을 찾지 못해 건너뜁니다"라고 알린다.** 형식을 추측해 쓰지 않는다. 조용히 지나가지 않는다.

4. **push**
   ```bash
   git push -u origin <branch>
   ```
   실패하면 **중단**한다. PR 생성으로 넘어가지 않는다. non-fast-forward면 원격 브랜치와의 차이를 보여주고 어떻게 할지 묻는다. force-push는 하지 않는다.

5. **PR draft**
   ```
   제목: <이슈 제목 기반. 프로젝트 커밋 컨벤션의 제목 규칙(타입·한글·50자)을 따른다>

   ## 요약
   <무엇을 왜, 2~3문장>

   ## 변경 내역
   - <커밋 단위로>

   ## 검증
   - <실행한 명령과 결과. 실행하지 않았으면 "자동 검증 수단 없음 — 수동 확인 항목: …">
   - <리뷰: 돌린 에이전트·모델, 반영/미반영 요약. 근거가 없으면 "리뷰 정보 없음">

   ## 이슈
   <Closes 또는 Refs — 아래 규칙> #<n>
   ```
   - 기본은 `Closes #<n>`. 이슈 본문에 **머지 밖의 완료 조건**(스토어 심사·운영 반영 확인 등)이 명시돼 있으면 `Refs #<n>`을 쓴다. 머지로 이슈가 닫히면 조기 종료다. `Refs`면 Status 자동 전이도 없으므로 완료 보고에 "이슈는 열려 있음, 완료 조건: …"을 적는다.
   - 실행하지 않은 검증·돌리지 않은 리뷰를 적지 않는다.
   - 승인 후 생성:
     ```bash
     gh pr create --base <base> --title "<제목>" --body-file <임시파일> --assignee @me
     ```
     실패하면 **중단**하고 오류를 그대로 보고한다. "이미 PR이 있다"는 오류면 그 URL을 보여주고 재리뷰·머지 중 무엇을 할지 묻는다. 재시도로 중복 PR을 만들지 않는다.
   - 범위 밖 발견 메모가 있으면 PR 생성 후 별도 이슈 등록을 제안한다 (draft 승인 후 `gh issue create --assignee @me`).

6. **머지 정책**

   | 조건 | 동작 |
   |---|---|
   | 설정 `merge: auto` | `gh pr checks <num> --watch`로 CI 통과를 기다린 뒤, 한 줄 확인("CI 통과. `<base>`에 머지합니다") 후 `gh pr merge <num> --<merge_method> --delete-branch` |
   | 설정 `merge: manual` | PR URL을 보고하고 멈춘다 |
   | 설정 없음, CLAUDE.md에 머지 정책 있음 | 그 정책을 따른다 (자동 머지 정책이면 위 `auto` 절차) |
   | 설정 없음, 정책도 없음 | `manual`과 같다 |

   - `--squash`는 `merge_method: squash`일 때만. 기본은 `--merge` (머지 커밋 보존).
   - CI가 실패하면 머지하지 않고 실패한 체크를 보고한다.
   - `--delete-branch`는 원격과 로컬 브랜치를 모두 지우고 기본 브랜치로 옮긴다. 이 경로에서는 아래 7번의 브랜치 삭제가 필요 없다.

7. **정리** — 사람이 웹에서 머지했거나 `--delete-branch` 없이 머지된 경우에만.
   ```bash
   git checkout <base> && git pull origin <base>
   git branch -d <branch>
   ```
   `merge_method`가 `rebase`·`squash`면 `-d`가 "not fully merged"로 실패한다. 그때는 PR이 머지됐음을 `gh pr view`로 확인한 뒤 확인받고 `-D`를 쓴다. Project Status의 Done 전이는 `Closes`에 의한 GitHub 자동화에 맡긴다. 직접 바꾸지 않는다.

## 게이트

- 잔여 리뷰 항목이 있을 때 PR 진행 확인 (1).
- PR draft 승인 (5).
- `merge: auto`여도 머지 직전 한 줄 확인 (6). 머지는 되돌리기 어렵다.
- 별도 이슈 등록 draft 승인 (5, 해당 시).
- `git branch -D` 확인 (7, 해당 시).

## 출력

- 히스토리: 작성한 파일/기록 위치, 또는 "규칙 없음 — 건너뜀"
- PR URL, base, 이슈 연결 방식 (`Closes`/`Refs`)
- 머지 여부, 머지 커밋 (머지 시)
- 정리 결과 (로컬 브랜치 삭제 여부)
- 등록한 별도 이슈 (있으면)
