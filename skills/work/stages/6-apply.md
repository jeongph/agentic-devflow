# 6. apply — 리뷰 반영

## 입력

- `리뷰 결과` (5-review 출력)
- 검증 명령 (계획에서)
- 설정 `simplify`, `review_model`

## 절차

1. **치명·중요 항목** — 항목마다 해당 코드를 열어 지적이 맞는지 확인한다.
   - 맞으면 고친다.
   - 틀렸거나(리뷰어가 맥락을 놓침) 범위 밖이면 고치지 않고 이유를 적어 "미반영"으로 남긴다.
   - 리뷰어의 말을 확인 없이 따르지 않는다. 리뷰어도 코드를 잘못 읽는다.

2. **제안 항목** — 목록을 보여주고 반영할 것을 고르게 한다. 사용자가 고른 것만 반영한다.

3. 반영 후 검증 명령을 실행하고 통과하면 커밋한다. 성격에 맞는 타입을 쓴다 (`fix:` 버그, `refactor:` 구조, `test:` 테스트 보강).

4. 치명·중요를 하나라도 반영했으면 **5-review를 다시** 돌린다. 고친 코드가 새 문제를 만들 수 있다.
   - 루프는 **최대 3회**. 3회 후에도 치명·중요가 남으면 잔여 목록과 함께 사용자에게 넘긴다. 무한 루프로 토큰을 태우지 않는다.
   - 재리뷰는 반영한 항목과 관련된 에이전트만 돌려도 된다 (예: 에러 처리만 고쳤으면 silent-failure-hunter + code-reviewer).

5. 치명·중요가 없으면 설정 `simplify`가 true일 때 정리를 한 번 한다.
   - `pr-review-toolkit:code-simplifier`를 `model: <review_model>`로 **1회** 호출한다. 대상은 이번 브랜치 변경분.
   - 검증 명령을 다시 실행한다. 통과하면 `refactor: 리뷰 후 코드 정리`로 커밋. 실패하면 `git checkout -- .`로 되돌리고 알린다. 정리가 동작을 바꿨다면 정리를 버리는 게 맞다.

## 게이트

- 제안 항목 선택 (2).
- 3회 초과 시 사용자 판단 (4).

치명·중요 반영은 게이트 없이 진행한다. 리뷰를 요청한 시점에 반영도 위임된 것으로 본다. 단, 미반영 사유는 반드시 보고한다.

## 출력

- 반영 내역 (항목 → 커밋)
- 미반영 항목과 사유
- 최종 검증 결과
- 리뷰 루프 횟수
